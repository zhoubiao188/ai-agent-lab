# Agent 工具调用成功率只有 36.7%,我把 720 次调用拆开看了

上周把售后 Agent 从 demo 推到灰度,第一天就被打回来:一个"查订单 + 查物流 + 算退款 + 提交退款"的任务,十次里能成六七次,剩下的要么报参数错误,要么超时,要么干脆返回一段"未能完成:xxx"。

这类问题最容易被糊过去的处理方式是加一句提示词:"请确保参数完整、格式正确,失败时重试。" 它看起来有用,实际上什么都没解决——你不知道失败发生在哪一层,也不知道改完之后到底好了多少。

所以我做了件笨事:给每条工具调用建一条完整记录,然后把 120 个任务、720 次调用、四组配置全跑一遍,让每种失败都有名字、有数量、有归属。这篇文章就是这份记录。

项目已开源(Spring Boot 3 + Spring Cloud Gateway + Vue3 / React 双前端),地址在文末,`mvn test` 直接跑,不需要任何 API Key。

---

## 一、先看失败长什么样

基线版本是最朴素的写法:模型给出调用、逐个执行、出错就抛给前端。720 次调用里,任务级成功率 **36.7%**,失败原因分布是这样的:

| 失败类型 | 次数 | 占比 |
| --- | --- | --- |
| 参数不合法 BAD_ARGUMENT | 79 | 54.1% |
| 超时 TIMEOUT | 22 | 15.1% |
| 上游 5xx | 22 | 15.1% |
| 限流 429 | 18 | 12.3% |
| 业务拒绝 BUSINESS | 5 | 3.4% |

注意有两个数字对不上:失败调用合计 146 次,但失败任务只有 76 个。原因是依赖会连坐——订单查询失败,后面依赖它的报价单、退款单全都会失败,一个根因变成三条报错。**排障时如果按调用数排序,你会去修三个地方;按根因排序,只需要修一个。** 所以后面所有的统计我都按"根因"归并。

这张表还说明一件事:参数错误占了一半以上。这意味着"重试"根本不是第一优先级——参数错的调用重试一百次还是错,它压根没打到上游。真正该先做的是**参数自纠正**。

但先别急着写代码。没有可复现的故障,你连"改好了"这三个字都说不出口。

## 二、故障必须能被复现,否则谈不上可靠性

我见过太多"可靠性"代码是这样的:重试逻辑写了三个月,线上从没触发过;熔断器的阈值是拍脑袋的 50%,从来没打开过;单测全是 happy path。

问题不在代码,在没有故障。所以我先写的是**故障注入器**,而不是重试器。

它有三个设计约束,每一条都是被坑出来的:

**1、确定性。** 同样的 seed + 工具名 + 调用 ID + 尝试次数,必须得到同样的结论。否则 L0 和 L3 面对的是两批不同的故障,成功率没有可比性,你也不知道涨的那几个点是不是运气。

**2、注入点在工具执行之前,并且跟尝试次数相关。** 重试之所以有用,是因为第二次尝试有可能成功。如果故障按"调用"注入,一个调用从头错到尾,重试就永远无效——那不是测重试,那是测放弃。

**3、按错误类型分别注入。** 超时、429、5xx、业务拒绝的分布必须接近真实,否则测出来的策略是给假数据调的。

```java
private Random draw(String tool, String callId, int attempt, long salt) {
    long h = seed;
    h = h * 0x9E3779B97F4A7C15L + tool.hashCode();
    h = h * 0x9E3779B97F4A7C15L + callId.hashCode();
    h = h * 0x9E3779B97F4A7C15L + attempt;
    h = h * 0x9E3779B97F4A7C15L + salt;
    return new Random(h);
}

public void maybeFail(String tool, String callId, int attempt) {
    for (ForcedFault f : forced) {
        if (f.tool().equals(tool)) throw toException(f.kind(), f.detail());
    }
    if (!enabled) return;
    Random rnd = draw(tool, callId, attempt, 1L);
    double d = rnd.nextDouble();
    if (d < cfg.timeoutRate()) throw ToolException.timeout(props.timeoutMs());
    d -= cfg.timeoutRate();
    if (d < cfg.rateLimitRate()) throw ToolException.rateLimited(20 + rnd.nextInt(40));
    d -= cfg.rateLimitRate();
    if (d < cfg.upstreamRate()) throw ToolException.upstream("remote service unavailable");
    d -= cfg.upstreamRate();
    if (d < cfg.businessRate()) throw ToolException.business("下游业务规则拒绝");
}
```

`attempt` 参与哈希是关键。同一个调用第 1 次被判超时,第 2 次会得到完全不同的随机数,所以才可能成功——这正是重试在真实世界里的样子。

顺带说一个副作用:因为 `callId` 参与了哈希,而线上 `callId` 里带着自增的 requestId,同一个 seed 跑两次会得到不同的故障。这在演示里很要命,所以我后来把线上入口的 `callId` 改成由 seed 派生:`"s" + Long.toHexString(seed)`。现在同一个 seed + 同一个任务,连重试退避的毫秒数都一模一样,时间线可以直接对着复盘。

## 三、错误分类比重试次数重要

大部分重试事故的根因不是"重试太多",而是"重试了不该重试的东西"。

把 404 重试三次,只是把"查不到"变成"查不到且更慢"。把"库存不足"重试三次,用户多等两秒看到同样的提示。把一笔已经超时退款重试三次,用户收到三笔钱。

所以第一步是分类,而不是计数。我的错误枚举和重试策略是一一对应的:

| 错误类型 | 典型来源 | 自动重试 | 理由 |
| --- | --- | --- | --- |
| TIMEOUT | 上游慢/网络丢包 | 是 | 上游可能只是抖动;但写操作要额外过幂等这一关 |
| RATE_LIMIT | 429 | 是 | 有明确的重试窗口,退避后大概率成功 |
| UPSTREAM_5XX | 502/503/504 | 是 | 瞬时故障的典型形态 |
| CONNECTION | 连接被拒/DNS | 是 | 同上 |
| BAD_ARGUMENT | schema 校验失败 | 否 | 重试一百次还是错,该修参数 |
| NOT_FOUND | 404 | 否 | 不存在就是不存在 |
| BUSINESS | 库存不足/状态不允许 | 否 | 业务规则拒绝,重试只会多等两秒 |
| CIRCUIT_OPEN | 熔断器打开 | 否 | 快速失败就是它的全部意义 |
| BUDGET_EXCEEDED | 任务预算耗尽 | 否 | 再试就是让用户等到超时 |

这张表里最容易争议的是 TIMEOUT 和 BUSINESS。前者确实"可能成功",但它也是唯一一个**可能已经产生了副作用**的错误类型——上游收到请求、执行了、只是没来得及回包。所以超时能不能重试,不取决于超时本身,取决于这个工具幂不幂等。

## 四、重试的四条铁律

四条规则,顺序就是它们在代码里的顺序,顺序错了会互相打架。

**1、只重试可重试的错误类型。** 见上表。

**2、非幂等写操作一次都不重试。** 这条规则救过我一次:退款接口超时后重试,用户收到两笔退款,追回来花了两周。现在的判断条件是 `writeOperation && !(idempotent && retryWrites)`,只要不是"写 + 声明幂等",直接放弃,交给上层补偿。

**3、退避必须带抖动。** 三个工具同时失败、步长都是 100ms,就等于自己造了一次小型 DDoS。用向下抖动(`1 - jitter * random()`)比正态抖动更简单,效果也够。

**4、Retry-After 超过退避上限时,放弃比提前重试更划算。** 上游明说 30 秒后再来,你 400ms 后就去敲,拿到的还是 429,只是多烧了一次配额,还多占了一次并发。

```java
public Decision decide(int attempt, ToolException e, ToolSpec spec) {
    if (attempt >= props.maxAttempts()) return Decision.stop("已达最大尝试次数");
    ErrorKind kind = e.kind();
    if (!kind.retryable()) return Decision.stop(kind + " 不属于可重试错误");
    if (spec.writeOperation() && !(spec.idempotent() && props.retryWrites())) {
        return Decision.stop("写操作非幂等,禁止自动重试");
    }
    long delay = backoff(attempt);
    if (kind == ErrorKind.RATE_LIMIT && e.retryAfterMs() > 0) {
        if (e.retryAfterMs() > props.backoffMaxMs()) {
            return Decision.stop("Retry-After 超过退避上限,提前重试无意义");
        }
        delay = Math.max(delay, e.retryAfterMs());
    }
    return new Decision(true, delay, kind + " 第 " + attempt + " 次失败");
}
```

还有一个不在上表里、但同样重要的约束:**整体预算**。单工具超时防的是一个坏依赖拖死全场,整体预算防的是"重试次数 × 工具数"把一次请求拖成 40 秒。所以每次尝试之前都要检查剩余预算,不够就直接返回 BUDGET_EXCEEDED,而不是排一个注定超时的重试。

## 五、参数自纠正:一半以上的失败,不需要问模型第二次

回到第一节那张表:参数不合法占了一半以上。这类错误有非常鲜明的特征——**它们几乎都是机械错误**,不需要模型"再想一遍"。

我把参数错误分成六类,按真实 trace 里的出现频次排序,做了个参数污染器,然后用修复器去覆盖:

| 污染类型 | 例子 | 修复规则 | 能否确定性修复 |
| --- | --- | --- | --- |
| 键名风格 | `order_id` | 归一化后匹配 schema 属性名 | 能 |
| 数字写成字符串 | `"199.0"` | 无损解析后转 number | 能 |
| 枚举大小写 | `Normal` | 忽略大小写 + 唯一前缀匹配 | 能 |
| 多带字段 | `timestamp` | 按 schema 白名单丢弃 | 能 |
| 布尔写成字符串 | `"true"` | 识别 true/1/yes/是 | 能 |
| 漏必填字段 | 缺 `orderId` | **不能**,需要任务上下文 | 否 |

前五类全部可以用规则改对,实测把参数错误从 79 次压到 1 次,而且不额外调模型、不增加延迟、行为可预测、可单测。

```java
public RepairOutcome repair(ObjectNode args, JsonSchema schema) {
    ObjectNode work = args.deepCopy();
    List<Repair> applied = new ArrayList<>();
    normalizeKeys(work, schema, applied);   // order_id -> orderId
    coerceValues(work, schema, applied);    // "199.0" -> 199.0
    fixEnums(work, schema, applied);        // Normal -> normal
    dropUnknown(work, schema, applied);     // 丢多余字段
    return new RepairOutcome(work, applied, validator.validate(work, schema));
}
```

这里有两个刻意的"不做",都是踩过坑才写下的。

**第一,校验器绝不偷偷做类型转换。** 早期版本我让校验器发现 `"12"` 就自动转成 12,结果很糟:修复逻辑永远不触发,也就永远不知道模型到底在哪些地方出错;报表上"参数错误 0 次",而线上退款金额全是被截断的整数。现在职责分得很清:校验器只报错,修复器负责改,两者都留痕。

**第二,小数转整数直接拒绝。** `12.7` 转 `integer` 字段,如果"顺手"截断成 12,这就是资金事故的起点。所以规则是:只有 `12.0` 这种整数值才转,`12.7` 保留原样继续报错。宁可失败。

不能确定性修复的那一类(漏必填),才轮到第二层:**把校验错误原文回灌给模型,只回灌一次。**

为什么只一次?因为两轮还改不对,大概率不是模型没看懂错误,而是任务本身不可完成(比如用户要退的订单根本不存在)。这时候继续问只是烧钱,正确动作是转人工。

回灌的内容也有讲究。只说"参数不对",模型只能瞎猜;说 `/paidAmount [TYPE_MISMATCH] 期望 number,实际是 string "$c1.paidAmount"`,它一次就能改对。所以我的 Violation 里存的是 JSON Pointer 路径 + 期望类型 + 实际值,拼成一句话直接塞回上下文。

顺带一个真实的坑:回灌之前必须先把 `$c1.paidAmount` 这种**引用占位符**排除掉。它本身是个字符串,当然过不了 number 校验,但这不是模型的错——这个字段要到执行时才有值。第一版没做这个过滤,结果每次运行都会白白多问模型一轮,日志里全是毫无意义的 rewrite。判断逻辑很简单:值是 `$callId.` 开头就跳过,真正的校验留给执行前那一刻。

## 六、并行:分层调度会让快调用等慢调用

六个调用里,订单查询、物流查询、库存查询互不依赖,报价单依赖订单,退款依赖报价单。串行执行 723ms,并行 352ms。

但"并行"这两个字,写法差别很大。我第一版是**分层**:按依赖深度分 wave,一层全部跑完再下一层。

实测只快了 40%,原因很直白:wave1 里最慢的是物流查询(200ms),而报价单只依赖订单查询(120ms),却要等物流跑完才能开始。这叫"陪跑"。

改成**依赖就绪调度**——谁的依赖齐了谁就跑——墙钟时间从 470ms 降到 330ms。实现上不是手写线程池,而是用 `CompletableFuture` 把依赖关系直接表达出来:

```java
for (ToolCall call : topological(calls)) {
    CompletableFuture<?>[] deps = call.dependsOn().stream()
            .map(futures::get).filter(Objects::nonNull)
            .toArray(CompletableFuture[]::new);

    CompletableFuture<ToolResult> future = CompletableFuture.allOf(deps)
            .handleAsync((v, err) -> {
                ToolResult blocked = blockedByDependency(call, done);
                if (blocked != null) return blocked;      // 依赖挂了,下游直接跳过
                permits.acquireUninterruptibly();          // 并发上限
                try {
                    return runOne(call, ctx, policy, done);
                } finally { permits.release(); }
            }, scheduler);
    futures.put(call.id(), future);
}
```

三个细节值得单独说。

**依赖从哪来?** 显式的 `dependsOn` 是最可靠的,但真实模型不会吐这个字段。所以还要扫参数里的 `$callId.field` 引用自动补依赖,两条路都走。

**参数怎么传?** 不是把上游结果整段塞给下游,而是只替换被引用的字段。`{"paidAmount": "$c1.paidAmount"}` 在执行前会被解析成 `{"paidAmount": 278}`。解析失败就快速失败并说明"引用无法解析",而不是带着一个字符串去调工具。

**并发要设上限。** 工具下游是别人的服务,无上限并发等于把你的流量放大成对方的事故,自己这边也只是把线程池堵死。默认 8,可配。

依赖失败时还有个容易忽略的点:下游要**跳过**,而不是带着空参数去执行。否则日志里会出现一堆"参数缺失"的次生错误,把真正的根因埋掉。这也是为什么第一节我强调"按根因归并"。

## 七、熔断:把慢失败换成快失败

重试解决偶发失败,但解决不了"依赖已经死了"。

当下游整体挂掉,重试 × 并发会让每个请求都排队等满超时,P99 从 300ms 冲到 3s,线程池被拖满,连健康检查都返回不了。熔断的作用只有一句话:**把慢失败换成快失败。**

实现是时间滑动窗口 + 半开探测,但有两个参数比算法更重要。

**第一个是最小样本量。** 低流量工具在 3 次调用里挂 2 次就被熔断,恢复还要等冷却期,可用性反而更差。我设的是 20 次。

**第二个是半开只放一个探测。** 冷却结束直接放开全量流量,等于给刚复苏的下游再来一次冲击。正确做法是先放一个请求,成功才关闸。

```java
public synchronized boolean tryAcquire() {
    long now = System.currentTimeMillis();
    if (state == State.OPEN) {
        if (now - openedAt >= openMs) {
            state = State.HALF_OPEN;
            probesInFlight = 0;
        } else {
            rejected++;
            return false;
        }
    }
    if (state == State.HALF_OPEN) {
        if (probesInFlight >= halfOpenProbes) { rejected++; return false; }
        probesInFlight++;
    }
    return true;
}
```

还有一个顺序问题:**参数校验必须在熔断之前。** 参数错的调用根本没打到上游,不该计入熔断统计,否则模型抽风一次就会把健康的下游熔断掉。我的流水线顺序是:

```
校验/修复 → 预算检查 → 熔断放行 → 故障注入 → 带超时执行 → 错误分类 → 退避重试 → 降级
```

最后一步「降级」有个硬边界:**只给读操作。** 写操作降级返回"成功"不是降级,是伪造。所以物流查不到可以返回"数据降级,建议人工复核",退款失败绝不可以返回一个假的退款单号。

## 八、四组对照实验

现在把四层机制做成开关,同一个编排器、同一批任务、同一个 seed、同一批故障序列,跑四组:

| 配置 | 成功率 | 降级 | 失败 | 成功任务均值 | P95 | 重试 | 参数修复 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| L0 裸调用 | 36.7% | 0 | 76 | 90ms | 96ms | 0 | 0 |
| L1 + 重试 | 65.0% | 0 | 42 | 111ms | 186ms | 60 | 0 |
| L2 + 参数修复 | 87.5% | 0 | 15 | 111ms | 173ms | 65 | 21 |
| L3 + 并行/熔断/降级 | 87.5% | 1 | 14 | 59ms | 100ms | 65 | 21 |

几个必须解释的数字。

**为什么 L1 的 P95 反而变差了(96ms → 186ms)?** 因为重试就是拿延迟换成功率。失败一次要退避再加一次完整调用,P95 涨一倍很正常。想同时要好延迟和好成功率,得靠 L3 的并行把基础耗时压下去——59ms,比 L0 还低。

**为什么 L3 的成功率没有再涨?** 这是整篇文章最重要的一句话:**剩下的失败,重试本来就不该救。** 我把失败按类型拆开:

| 配置 | 参数错误 | 超时 | 5xx | 429 | 业务拒绝 | 依赖跳过 |
| --- | --- | --- | --- | --- | --- | --- |
| L0 | 79 | 22 | 22 | 18 | 5 | 0 |
| L1 | 52 | 5 | 4 | 1 | 5 | 0 |
| L2 | 1 | 5 | 4 | 2 | 5 | 0 |
| L3 | 0 | 4 | 4 | 2 | 5 | 1 |

L2 之后,链路故障(超时/5xx/429)已经被重试压到 10 次以内,参数错误从 79 降到 1。剩下的 5 次业务拒绝,是退款金额已经退完、状态不允许这类**业务规则**——重试它们只会让用户多等两秒看到同样的结果。

还有那 1 次"依赖跳过",它来自一个更隐蔽的天花板:工单接口是非幂等的,一次超时就只能失败,而工单失败会让整个任务判为失败。

## 九、最后 12.5% 不是机制能救的

顺着上面的线索,我只改了一件事:给工单接口加幂等键,声明它可重试。然后同样跑一遍:

| 配置 | 改造前 | 改造后 |
| --- | --- | --- |
| L1 + 重试 | 65.0% | 71.7% |
| L2 + 参数修复 | 87.5% | 95.0% |
| L3 + 并行/熔断/降级 | 87.5% | 95.0% |

一个接口的幂等声明,值 7.5 个百分点。

这就是我想说的结论:**可靠性机制的上限,由业务语义决定。** 重试策略再精致,遇到一个"不能重试的写接口"也只能绕开;熔断再灵敏,也救不回一个本来就该被业务拒绝的请求。所以调优的顺序应该是:

**1、** 先把参数修好——它是最大的一块,而且完全在你自己手里。

**2、** 再把读接口的重试和降级做扎实——这部分收益最确定。

**3、** 然后回头改业务接口的幂等性——收益最大,但需要跨团队。

**4、** 最后才是调超时、退避、熔断阈值这些参数。

顺序反了,就会出现"把超时从 800ms 调到 1200ms,成功率涨了 3 个点,然后以为是自己调参调得好"这种自欺欺人的结论。

## 十、可以直接抄走的清单

**错误分类:**

**1、** 所有工具异常必须带类型枚举,禁止靠 message 字符串判断(上游改一次文案,重试策略就会静默失效)。

**2、** 404、业务拒绝、参数错误永不重试。

**参数:**

**3、** 校验器只校验,不做类型转换;转换交给修复器,两者都留痕。

**4、** 确定性修复优先,回灌模型只回灌一次,并且必须带 JSON Pointer 路径。

**5、** 绝不为了"跑通"而截断小数。

**重试:**

**6、** 非幂等写操作的重试开关永远是关的,除非工具声明幂等且调用带幂等键。

**7、** 退避带抖动,并且尊重 Retry-After;Retry-After 超过上限就放弃。

**8、** 每次尝试前检查整体预算,而不是只依赖单次超时。

**并行:**

**9、** 用依赖就绪调度,不要用固定分层;分层会让快调用等慢调用。

**10、** 依赖失败时下游必须跳过,不要带着空参数硬跑。

**11、** 并发必须有上限,那是给下游留活路。

**熔断与降级:**

**12、** 熔断按工具独立,最小样本量别低于 20,半开只放一个探测。

**13、** 参数校验放在熔断之前,别把参数错误算进下游可用性。

**14、** 降级只给读操作;写操作降级等于伪造。

**可观测:**

**15、** 每次调用记录 attempts、每次的错误类型、退避时长、修复了哪些字段——排障时这些比结果本身有用。

**16、** 成功率要区分"成功"和"降级后成功",把降级算进成功率是自欺欺人。

**17、** 延迟只统计成功的任务,否则会得出"越不靠谱越快"。
