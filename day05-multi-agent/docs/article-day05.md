上周把一个售后 Agent 从单 Agent 改成 Planner / Executor / Critic 三角色,灰度第一天就出了一笔账。

用户的原话是「A10003 不想要了,能退多少退多少」。Agent 跑完了,三步,每一步都返回 200,最后回了一句「已完成退款,金额 ¥199」。

对账的时候发现,这个订单的可退金额是 ¥278。

差额 79 块,不是算错的,是**模型自己编的**。它拿不到报价单,于是把金额写成了字面量 199,退款接口校验通过(199 在 0.01~100000 之间)、执行成功、返回退款单号。整条链路上没有任何一个环节报错。

这就是多 Agent 时代最贵的一类故障:**任务拆错了,但每一步都对。**

Day04 那篇写的是"工具调用可不可靠"——超时、重试、参数修复。那套机制上线之后,工具层的失败率从 63% 降到 5%。但这次的事故,工具层一点责任都没有:退款接口确实被调用了,参数也确实合法,只是**这个调用本来就不该发生**。

所以今天这篇只讲一件事:计划错了怎么发现。

## 一、先看那条 trace

这是 C0 组(什么防线都没有)跑 T03 的真实事件流,只截了计划部分:

```
plan

  {"id":"s1","tool":"order.query","dependsOn":[],"covers":["order"],
   "produces":["orderId","sku","paidAmount","refundedAmount","status"],
   "args":{"orderId":"A10003"}},
  {"id":"s2","tool":"refund.quote","dependsOn":["s1"],"covers":["quote"],
   "produces":["quoteId","amount"],
   "args":{"orderId":"A10003","paidAmount":"$s1.paidAmount","refundedAmount":"$s1.refundedAmount"}},
  {"id":"s3","tool":"refund.submit","dependsOn":[],"covers":["refund"],

   "args":{"reason":"七天无理由","quoteId":"Q00000","amount":199.0},"write":true}
```

看出问题了吗?第三步 `s3` 的 `dependsOn` 是空的,`amount` 是数字 199.0,`quoteId` 是 `"Q00000"`。

而第二步 `s2` 明明算出了报价。它就在计划里,只是**没人依赖它**。

执行阶段的返回是:

```

```

`step_ok` 三次,`claimed` 是 true(系统认为成功),`success` 是 false(金标准判定失败):

```

        AMOUNT_MISMATCH:报价 278.0 实退 199.0
```

报价 278,实退 199。这个差额在线上的含义是:用户少拿了 79 块,而且他很可能不会发现。

## 二、"每一步都 200"为什么是最危险的信号

工程上有一个很自然的指标:调用成功率。它对 Day04 那类问题(超时、限流、上游 5xx)非常有效,但对今天这类问题几乎是反向的。

我在这套代码里把两个概念分开:

**claimed** —— 系统自己认为成功。定义是所有步骤都执行成功,没有异常。

**success** —— 金标准判定成功。定义是用户的每个诉求都被覆盖、写操作真的落地、金额能溯源到上游。

C0 组的 20 个任务里:

| 指标 | 数量 |
|---|---|
| 系统宣称完成(claimed) | 20 / 20 |
| 金标准通过(success) | 10 / 20 |
| 假成功(claimed 且 !success) | 10 |

**50% 的任务在"全绿"的状态下交付了错误结果。**

更细一点,这 10 个假成功的成因分布是:

| 原因 | 次数 | 用户看到什么 |
|---|---|---|
| 拆漏(UNDER_COVER) | 5 | 答案里少了一个诉求,比如没建工单 |
| 写操作参数不可溯源(WRITE_UNGROUNDED) | 5 | 退了一笔编出来的金额 |
| 金额与报价不一致(AMOUNT_MISMATCH) | 5 | 少退/多退,差额从几块到几十块 |
| 写操作没落地(WRITE_MISSING) | 2 | 说退款了,其实计划里根本没有退款这一步 |

注意 `WRITE_UNGROUNDED` 和 `AMOUNT_MISMATCH` 都是 5 —— 是同 5 个任务同时中了两个,因为"金额是编的"必然导致"和报价对不上"。

所以问题不是"成功率不够高",而是**我们在用错误的指标衡量成功**。这是多 Agent 协作里第一个必须改的东西:验收标准要站在用户那一侧,不能站在步骤返回码那一侧。

## 三、让计划变成可以验收的东西

要判断"计划错没错",前提是计划得**可被机器检查**。一串 `{tool, args}` 是不够的——它能表达"调什么",表达不了"为什么调"。

所以我给每个步骤加了四个声明:

```java
public record Step(
        String id,
        String title,
        String tool,
        ObjectNode args,
        List<String> dependsOn,   // 显式依赖
        List<String> covers,      // 这一步覆盖了用户的哪个诉求(意图槽位)
        List<String> produces,    // 这一步承诺产出哪些字段
        List<String> consumes     // 这一步需要别人产出的哪些字段
) {}
```

这四个字段各自对应一种检查:

- `covers` → 拆漏。用户要 3 件事,计划里 `covers` 的并集只有 2 个,差额就是漏项。
- `dependsOn` + 参数里的 `$s1.paidAmount` 引用 → 拆错。引用了上游却没写进依赖,数据流就断了。
- `produces` → 计划说谎。声明产出 `amount`,结果里没有这个字段,说明模型在计划里写了漂亮话。
- `consumes` → 数据流审计。谁的数据从哪来,能不能画出完整的一条链。

还有一件事:**Plan 必须是 DAG,不能是 List**。

列表只能表达"先后",表达不了"可以并行",更要命的是——**列表没有环的概念**。模型给出的计划真的会出现 A 依赖 B、B 又依赖 A。用列表存,这种错误永远不会暴露;用图存,一次拓扑排序就报出来了。

```java
public Optional<List<Step>> topological() {
    // 一轮轮取"依赖都已就绪"的步骤,取不动了就是有环
    // 返回 empty 表示计划不可执行,调用方必须显式处理,不能拿截断的顺序硬跑
}
```

## 四、三类拆错,三种修复成本

这是整篇文章我认为最有价值的一张表。三类错误的检测手段、修复动作、代价完全不同,混在一起谈"要不要加重试"是没有意义的。

| 缺陷 | 典型症状 | 谁能发现 | 修复动作 | 成本 |
|---|---|---|---|---|
| 拆漏 | 用户说了 3 件事,计划只做 2 件 | 意图覆盖核对 | 机械补步,不用模型 | 低 |
| 拆错 | 依赖断开,金额由模型自己编 | 静态校验(参数溯源) | 重规划,且必须在写之前 | 高 |
| 拆多 | 一步能做完拆成两步 | 静态校验(重复步骤) | 重规划去冗余 | 中 |

三个结论:

**1、拆漏是唯一能机械修的。** 因为槽位和步骤一一对应,补一个步骤不需要"重新想一遍整体计划"。

**2、拆错必须在写操作落地之前发现。** 一旦退款的请求发出去了,事后重规划救不回来——钱已经走了。这类错误只有"执行前拦截"这一条路。

**3、拆多最无害,也最容易被忽略。** 它不影响结果正确性,只多花一次调用。但它是最值得量化的:一次多余调用 = 一次额外延迟 + 一次额外失败概率,而且会随着 Agent 变复杂而指数增长。

## 五、静态校验:九条规则里真正救命的三条

校验器一共九条规则:重复 id、未注册工具、悬空依赖、成环、引用未声明依赖、字段无人产出、步数超限、重复步骤、写操作不可溯源。

前六条是结构卫生,写起来无聊但必须有。真正救命的是后三条:

```java
// 1. 参数引用了上游,却没写进 dependsOn —— 顺序错最典型的机器可读形态
if (refs.stream().anyMatch(r -> !step.dependsOn().contains(r.stepId()))) {
    out.add(violation(MISSING_DEPENDENCY, step.id(),
            "参数引用了 " + ref + ",但 dependsOn 里没有 " + ref.stepId()));
}

// 2. 同一工具 + 同一参数出现两次
for (Step step : plan.steps()) {
    String sig = step.tool() + "|" + step.args();
    if (!signatures.add(sig)) {
        out.add(violation(REDUNDANT_STEP, step.id(), step.tool() + " 用同样的参数又调了一次"));
    }
}

// 3. 写操作的金额/单号必须是引用,不能是字面量
static final Set<String> DERIVED_ARGS =
        Set.of("amount", "quoteId", "paidAmount", "refundedAmount", "refundId");

if (spec.writeOperation()) {
    for (String arg : derivedArgsPresent(step)) {
        if (!isRef(step.args().get(arg))) {
            out.add(violation(UNGROUNDED_WRITE, step.id(),
                    arg + " = " + step.args().get(arg) + " 是字面量,不是上游算出来的"));
        }
    }
}
```

第三条是我最想强调的。它的判断标准不是"参数合不合法",而是"**这个值是怎么来的**"。

`amount = 199` 完全合法:schema 说是 0.01~100000 的数字,类型对、范围对。但它不是算出来的,是编的。而"钱"这种东西,编出来的金额就是事故。

这条规则有效的前提是:工具声明里必须能区分"派生参数"和"输入参数"。我把 `amount / quoteId / paidAmount / refundedAmount / refundId` 这几类挂在一个常量里,谁家写这类系统,这个集合都得自己维护一份——它不是通用规则,是业务规则。

## 六、覆盖核对:拿什么对账

覆盖率这件事,难点不在算法,在于**你得先能写出"什么算对"**。

我的做法是给每个任务配一份金标准,就是用户诉求展开后的槽位列表:

```java
add(TaskSpec.of("T02", "A10002 收到的是坏的,退款,再帮我催一下物流,客服也要介入",
        "A10002", "SKU-1002", 1, "质量问题",
        List.of("order", "logistics", "quote", "refund", "ticket"),  // 金标准:5 个槽位
        PlanFlaw.UNDER_COVER));
```

核对本身只有三行:

```java
public CoverageReport check(Plan plan, TaskSpec task) {
    Set<String> covered = new LinkedHashSet<>();
    for (Step step : plan.steps()) {
        covered.addAll(step.covers());
    }
    Set<String> missing = new LinkedHashSet<>(task.slots());
    missing.removeAll(covered);
    return new CoverageReport(task.slots(), covered, missing);
}
```

补步也是三行,而且**不调用模型**:

```java
public Plan patch(Plan plan, TaskSpec task, CoverageReport report) {
    Plan next = plan;
    int seq = plan.size();
    for (String slotKey : report.missing()) {
        Step step = StepTemplates.build(next, task, Slot.of(slotKey), "s" + (++seq));
        next = next.plus(step);
    }
    return next;
}
```

补出来的步骤天然接得上,因为它要的数据都来自**已经在计划里**的上游步骤,直接追加到末尾仍然是合法拓扑序。

这里有个判断值得说清楚:**补步该不该交给模型?**

我的答案是:漏项不该。漏项的本质是"少了一个已知的槽位",不是"想不出怎么做"。让模型重想一遍,它会顺手把别的步骤也改了,引入新的不确定性;而补一步是确定性的,同样的输入补两次结果完全一样。实验里 C2 组(校验 + 覆盖 + 补步)把拆漏 5 个任务全部修好,一次模型调用都没用。

## 七、事后复核查什么、查不到什么

Critic 在整条链路里是最后一道,它检查的不是"步骤成功了吗",而是"**计划的承诺兑现了吗**"。四件事:

**1、覆盖** —— 但只认成功执行的步骤。计划里有不代表执行了。

**2、产出** —— 声明 `produces: [paidAmount, status]`,结果里真有这些字段吗。模型很喜欢在 produces 里写一堆漂亮字段,实际只返回一个 id。

**3、写操作落地** —— 承诺退款,就必須有一条 `refund.submit` 的成功记录。

**4、溯源** —— 写操作的金额是算出来的还是编出来的。这条只有拿计划和执行记录对账才能看出来。

复核结论不是"通过/不通过",而是**可执行的差异清单**,分四种处置:

| 结论 | 含义 | 处置 |
|---|---|---|
| PASS | 承诺全部兑现 | 直接交付 |
| PATCH | 只缺诉求,不缺结构 | 机械补步,便宜 |
| REPLAN | 计划本身错了 | 重写计划,贵,且写操作可能已经落地 |
| FAIL | 写操作失败,救不回来 | 如实告诉用户,绝不重试 |

**但 Critic 查不出"拆多"。**

这是它的能力边界,我在单测里专门固化了这条:

```java
@Test
@DisplayName("事后复核发现不了拆多:多调一次读接口,结果照样正确")
void redundantIsInvisibleAfterExecution() {
    List<StepOutcome> outcomes = new ArrayList<>(healthy());
    outcomes.add(output("s4", "order.query", 199.0, 0.0, true));   // 多调一次

    assertThat(critic.review(plan, task, outcomes).verdict()).isEqualTo(Verdict.PASS);
}
```

多调一次订单查询,结果一模一样,链路上没有任何异常。绕远路只有静态校验能看见——**这就是为什么两层都要有:静态看形状,动态看兑现。**

## 八、重规划的三条纪律

重规划是最容易写成灾难的一步。我踩了一个坑,也定死了三条规矩。

**坑:重规划之后金额还是错的。**

第一次实现时,幂等键是这样算的:`idem-{taskId}:{stepId}`。

于是 C3 组的行为是:校验发现金额不可溯源 → 重规划 → 新计划里退款金额正确(¥278)→ 执行 `refund.submit` → 幂等键命中第一次那次错误请求 → **返回 199 的旧结果**。

日志上看一切都对:重规划成功了,退款也返回了。但钱还是错的。

根因是幂等键的语义错了:它应该标识"**这一次请求**",而不是"这一步"。改成由请求内容派生:

```java
String idempotencyKey = ctx.idempotencyKey() + ":" + step.id() + ":"
        + Integer.toHexString(resolved.toString().hashCode());
```

改对之后的请求,内容不同,键就不同,不会被第一次的错误请求挡回去。同时同样的请求重复执行,键相同——幂等语义还在。

**纪律一:重规划只改结构,不重试同一步。**

如果重规划拿回来一份和原来一模一样的计划,直接放弃,不要执行:

```java
Plan replanned = planner.plan(task);
if (replanned.fingerprint().equals(plan.fingerprint())) {
    emit("replan_abort", "重规划结果与原计划一致,停止重试");
    return conclude(...);
}
```

原地打转是重规划最常见的失败形态,没有这个判断,`maxReplans=1` 也会被一次无意义的执行浪费掉。

**纪律二:复用已完成步骤的结果。**

重规划后重新执行,必须跳过已经成功的步骤。否则"重规划"就等于"把写操作重放一遍"——那是重复退款的生产事故,不是修复。

```java
if (done.contains(step.id())) {
    emit("step_cached", step.id());
    continue;
}
```

**纪律三:写操作失败绝不重规划。**

这一点直接沿用 Day04 的结论:**非幂等写操作永不自动重试**。在这里它表现为:

```java
if (failure instanceof WriteStep && !spec.idempotent()) {
    return Verdict.FAIL;   // 不 REPLAN,不重试,如实报告
}
```

写操作失败只有两种结局:幂等键能证明它没落地,或者人工介入。没有第三种。

## 九、四组数据

20 个任务,6 个计划正确、14 个带固定缺陷(5 拆漏 / 5 拆错 / 4 拆多),4 组配置各跑一遍,共 240 次任务执行。所有缺陷由任务固定指定,不随机,同一批数据跑两次结果完全一致。

| 配置 | 任务成功 | 假成功 | 被拦下 | 平均步数 | 平均延迟 | P95 | 重规划 |
|---|---|---|---|---|---|---|---|
| C0 无契约 | 10/20 (50.0%) | 10 | 0 | 3.6 | 439ms | 632ms | 0 |
| C1 静态校验 | 6/20 (30.0%) | 5 | 9 | 1.85 | 227ms | 625ms | 0 |
| C2 覆盖补步 | 11/20 (55.0%) | 0 | 9 | 2.1 | 255ms | 635ms | 0 |
| C3 复核重规划 | 20/20 (100%) | 0 | 0 | 3.65 | 447ms | 633ms | 9 |

按缺陷类型拆开看,才看得出每组到底救了什么:

| 缺陷类型 | 任务数 | C0 | C1 | C2 | C3 |
|---|---|---|---|---|---|
| 干净 | 6 | 6 | 6 | 6 | 6 |
| 拆漏 | 5 | 0 | 0 | 5 | 5 |
| 拆错 | 5 | 0 | 0 | 0 | 5 |
| 拆多 | 4 | 4 | 0 | 0 | 4 |

失败原因的分布:

| 配置 | 失败原因 |
|---|---|
| C0 | 拆漏 5、金额不可溯源 5、金额不一致 5、写操作未落地 2 |
| C1 | 拆漏 5、被校验拦下 9、写操作未落地 2 |
| C2 | 被校验拦下 9 |
| C3 | 无 |

三段解读。

**第一段:加了校验,成功率反而掉了 20 个百分点。**

C0 的 50% 掉到 C1 的 30%。这不是退步,是把"假成功"挤掉了——C0 的 10 个成功里有 4 个是拆多任务(结果对、只是慢),另外 6 个是干净任务;而 C1 把 9 个结构错误的任务直接拦死,一步都没执行。

**关键差别在"错误写操作的落地次数":C0 是 5,C1 是 0。**

只加校验不加修复,等于把 bug 从前端搬到错误页。它能止损,但提不高成功率。这一点如果不讲清楚,团队看到成功率下降就会把校验关掉——那是灾难的开始。

**第二段:覆盖核对把假成功清零了。**

C1 的 5 个假成功全是拆漏:计划跑完了、退款成功了、工单没建,用户少拿一个诉求。C2 加上覆盖核对后,假成功从 5 变成 0,成功率从 30% 回到 55%——恰好和 C0 齐平,但性质完全不同:C0 的 55% 里有一半是蒙对的,C2 的 55% 是确定的对。

**第三段:只有"拦下即重规划"才能把结构错误救回来。**

C3 和前两组的关键差别是一个 if:校验失败之后,不是 `return failed`,而是先重规划一次。

这一步之所以能成功,原因是**此时写操作还没落地**。验证顺序是:规划 → 校验 → 覆盖 → 执行 → 复核。所有结构错误都在执行之前被发现,所以重规划是安全的。

如果把这个顺序换一下——先执行再校验——那 C3 的成功率会掉回 C0,因为钱已经退错了。

最后说一句数据的边界:20 个任务、100% 这个数字不好看,因为它太干净了。所有缺陷都是"可以在写操作之前判定"的类型,而真实世界的长尾是**你说不清金标准**——用户说"看着办",你连槽位都拆不出来。这套方法能解决的是"说清楚了但拆错了",不能解决"没想清楚"。

## 十、可以直接抄走的清单

**关于计划的结构:**

**1、** 计划存成 DAG,不要存成列表。环、悬空依赖、并行度,只有图能表达。

**2、** 每个步骤必须声明它覆盖了哪个诉求。这是拆漏检测的唯一依据。

**3、** 每个步骤必须声明产出了哪些字段。声明了没兑现,比不声明更有害,因为它会让复核误判为通过。

**4、** 参数里引用上游数据时,依赖必须显式写。不要指望从 `$s1.amount` 里反推——反推只能兜底,不能当机制。

**关于校验:**

**5、** 校验放在花掉第一次调用的前面。这是校验唯一有价值的位置。

**6、** 写操作的关键参数(金额、单号)必须能溯源到上游计算。字面量一律拦。

**7、** 同一工具同参数出现两次就是拆多,直接拦。不要因为"结果对"就放过它。

**关于覆盖:**

**8、** 用户诉求要展开成槽位,和金标准对账。这件事必须在写代码之前做,做不到就先别上多 Agent。

**9、** 漏项用机械补步,不要交给模型重想。确定性修复比"再想一遍"便宜且可靠。

**关于复核与重规划:**

**10、** 复核要按"承诺是否兑现"查,不要按"步骤是否成功"查。后者是过程指标,前者才是验收。

**11、** 重规划必须复用已完成步骤的结果,并且次数上限设为 1。第二次重规划改对的概率极低,延迟却要翻倍。

**12、** 幂等键要由请求内容派生,不能只用任务 id。否则"改对之后的第二次请求"会被"第一次的错误请求"挡回去——这是我这次踩的最深的一个坑,重规划看起来成功了,钱还是错的。
