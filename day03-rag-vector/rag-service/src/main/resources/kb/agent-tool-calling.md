# AI Agent 工具调用工程化

## Function Calling 的协议细节

模型返回的工具调用不是一次性完整的 JSON,而是增量分帧到达的。第一帧带 index 与 name,后续帧只带 arguments 的片段,必须按 index 归组、按到达顺序拼接,拼完再解析。如果每帧都尝试解析 JSON 就会不断失败。另外流式响应里可能先输出一段自然语言再发起工具调用,这段文本是否展示给用户,是需要产品决策的:展示了却马上被工具结果覆盖,用户会觉得闪。

## 工具描述是提示词的一部分

name、description、参数 schema 三者共同决定模型会不会正确调用。description 要写清"什么时候用"而不是"这个工具做什么",例如"查询订单物流状态,仅在用户提供订单号时调用"。参数用 enum 限定取值范围,比在描述里说"必须是这三个之一"可靠得多。参数越少越好,超过五个参数的工具,模型填错的概率显著上升。

## 超时与失败的处理

工具执行必须有超时,而且要区分两类:客户端超时(放弃等待)与服务端取消。只做前者的话,后端任务继续跑,资源被白占。Java 里用 Future.get(timeout) 只是放弃等待,配合 cancel(true) 才能尝试中断线程,但要注意线程必须响应中断。工具失败时不要把异常堆栈直接抛给模型,应该返回结构化错误,让模型有机会换参数重试或向用户解释说不了。

## 幂等与副作用

写操作类工具必须支持幂等键。模型在超时后重试是常态,如果没有幂等保护,一次"创建工单"会变成三张单。做法是让调用方在参数里带 requestId,服务端用唯一索引或者 Redis SETNX 去重,重复请求直接返回第一次的结果。读操作相对安全,但也要注意限流,模型可能在一个推理步骤里连续发起五次同样的查询。

## 多步推理的终止条件

Agent 循环必须有硬上限,否则模型在两个工具之间反复横跳会耗尽预算。除了最大步数,还要加上重复检测:同样的工具加同样的参数第二次出现就直接判定为循环,强制收束成最终回答。另外要统计累计 token,接近上下文上限时提前终止并降级成"基于已有信息回答"。

## 工具结果的裁剪

数据库查询返回两百行,原样塞回上下文会瞬间撑爆窗口,并且淹没有效信息。工具应该自己负责裁剪:限制返回条数,超出的部分给出总数与提示"结果已截断,可加筛选条件"。字段也要裁,时间戳、内部 ID 这类模型用不上的字段直接去掉。经验上单个工具结果控制在五百 token 以内,模型的理解质量最好。

## 观测与回放

一次 Agent 请求会横跨多次模型调用与多次工具执行,没有 traceId 就没法排查。每一跳都要记录:输入消息摘要、模型输出的工具名与参数、工具耗时、结果摘要、累计 token。这些记录同时是回放数据集,改了提示词之后可以拿历史请求重跑,对比工具调用准确率有没有下降。没有回放能力的 Agent 系统,每次调优都是重新赌博。
