# RAG 检索工程实践

## 固定长度分块的三个副作用

按固定字符数切块最省事,但会在三个地方出问题:句子被从中间截断,导致关键词跨块;表格与代码块被切碎,语义完全丢失;跨块的问题需要两块拼起来才能回答,单块召回必然失败。工程上的折中是按结构化边界优先、长度兜底:先按标题切小节,小节超过上限再按句子切,句子还超长才硬切。重叠区 overlap 的作用不是"多给点上下文",而是防止边界信息丢失,经验值是块长的百分之十五左右。

## 块大小与召回率的权衡

块越大,单块携带的信息越完整,但向量会被多个主题平均掉,相似度变得不敏感;块越小,匹配越精准,但容易缺上下文导致大模型答不全。中文技术文档的经验区间是三百到六百字,英文是两百到四百 token。判定方法不是拍脑袋,而是拿评测集跑一遍不同块长下的 recall@5 与答案正确率,选择拐点。块长一旦变化,索引必须全量重建,所以要在项目初期就定下来。

## BM25 与向量检索的分工

BM25 依赖词项精确匹配,对术语、错误码、类名、配置项这类查询几乎无敌,但遇到同义改写就哑了。向量检索靠语义空间的距离,能跨过同义词和语序差异,但对专有名词、数字、代码标识符不敏感,甚至会把毫无关系的块排在前面。真实场景里两类查询都存在,所以生产系统基本都是混合检索,而不是二选一。

## RRF 融合为什么比加权分数更稳

BM25 的分数是无上界的实数,余弦相似度在 0 到 1 之间,两者直接加权必须做归一化,而归一化本身依赖当次结果分布,换个查询尺度就变了。RRF(Reciprocal Rank Fusion)只用排名不用分数,公式是每个来源贡献 1/(k + rank),k 通常取 60。它的好处是对分数量纲完全不敏感,坏处是丢掉了"第一名领先第二名很多"这种信息。工程上先用 RRF 拿到稳定的基线,再考虑学习型融合。

## 重排的价值与代价

召回阶段追求的是不漏,所以 topK 会给到二十甚至五十,重排阶段才追求准。Cross-Encoder 把 query 与文档拼接后一起送进模型,能建模细粒度的交互,效果显著优于双塔向量,但复杂度是 O(n),只能对小候选集做。工程替代方案是特征重排:词项覆盖率、连续短语命中、标题命中、块长惩罚、命中位置,线性加权,毫秒级完成,效果能拿到 Cross-Encoder 的六七成。

## 评测集的构造方法

没有评测集的 RAG 就是在盲调。最小可用评测集包含三层:真实用户问题(从日志里捞)、同义改写(人工改写成三种问法)、边界问题(知识库里根本没有答案的)。每条样本标注 gold 文档与定位锚点,锚点用一段特征短语而不是块 ID,这样分块策略调整后标注不会失效。规模上五十到两百条就能看出趋势,关键是覆盖不同类型而不是追求数量。

## 召回指标的取舍

recall@k 衡量前 k 个结果里有没有正确块,是 RAG 的第一指标,因为没召回就不可能答对。MRR 只看第一个正确结果的位置,适合"只有一个标准答案"的场景。NDCG 考虑多级相关性与位置折损,适合一个问题对应多个部分相关文档的情况。注意 recall@k 会随 k 单调上升,所以不同系统比较时必须固定 k,否则数字毫无意义。

## 离线指标好但线上答不好的原因

最常见的原因是上下文拼接方式:召回对了,但把五个块无差别拼接,噪声块淹没了正确块,模型被带偏。其次是提示词没有要求引用来源,模型自由发挥。第三是块里缺少必要的主语,比如"它默认是 200",模型无法判断"它"指什么。解决办法是在块头注入文档标题与小节名,让每个块自带语境,这一招对提升答案准确率非常有效。
